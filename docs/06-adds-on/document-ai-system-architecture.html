Document AI Platform Blueprint

单据识别 + 系统管控平台架构设计

建议把它设计成「业务应用层 + 文档智能 PaaS + 模型服务层 + 数据治理层 + 云原生 Infra」五层结构。核心不是只把 OCR 跑起来，而是让识别结果可配置、可审核、可追溯、可迭代。

一句话判断

如果未来会接多个业务线、多类票据/合同/表单，不要做成单点 OCR 工具；要从 Day 1 按平台化建设。

多租户Human-in-the-loop模型路由审计追踪私有化/混合云

01目标系统边界

业务目标

把非结构化单据变成可信数据

支持发票、采购单、报销单、合同、物流单、银行流水、身份证明等输入，输出标准字段、置信度、版面证据和可追溯处理记录。

管理目标

让业务团队自己配置规则

字段模板、校验规则、审批流、异常队列、权限、租户策略都应可配置，避免每加一种单据都改代码。

平台目标

模型、任务、数据、成本都可管

后续模型会不断换代，架构要允许 OCR、VLM、LLM、规则引擎和人工审核共同协作，而不是绑定单一模型。

04PaaS 层应该怎么设计

平台能力

把识别能力产品化，而不是 API 拼装

模板中心
定义单据类型、字段 schema、字段别名、必填项、正则/枚举/范围校验。
规则引擎
支持字段级规则、跨字段规则、外部主数据核验、低代码配置。
流程编排
不同单据走不同 Pipeline，可插拔 OCR、VLM、LLM、人工审核节点。
租户治理
资源配额、QPS、数据隔离、模型白名单、成本中心、审计日志。
结果版本
原始识别、规则修正、人工修正、最终提交要留版本，不要只存最终值。
关键取舍

先做配置化，再考虑“全自动”

单据系统最容易踩的坑是过早承诺 100% 自动化。更稳的路线是：高置信自动通过，低置信进入人工队列，人工修正反哺模板和评测集。

  • 模板不是固定坐标，而是字段 schema + 规则 + 示例 + 证据区域。
  • Pipeline 要异步化，上传接口只返回 task_id，结果通过轮询/回调拿。
  • 所有模型输出必须带置信度和 evidence，不然审核无法提效。
  • 管控后台要能改阈值、灰度模型、回滚版本。

06模型层设计

推荐组合

不要押单一模型，做模型编排

  • OCR 模型：负责文字识别、坐标、行块、表格基础结构。
  • Layout 模型：识别标题、表格、键值对、印章、签名、复选框。
  • VLM：处理复杂版式、跨页字段、多语言、低模板化单据。
  • LLM：做字段归一化、语义校验、业务解释、异常原因生成。
  • 规则/知识库：做确定性校验，比如税号、金额合计、供应商主数据。
模型治理

上线模型前要有评测闭环

  • 建立 Golden Set：按单据类型、语言、质量、版式、渠道分层采样。
  • 字段级指标：Exact Match、归一化后准确率、漏抽率、误抽率。
  • 业务级指标：自动通过率、人工修改率、平均处理时长、返工率。
  • 灰度发布：按租户/单据类型/比例切流，支持模型版本回滚。
  • 成本控制：简单票据走轻模型，复杂单据才触发 VLM/LLM。

吞吐、SLA、错误率、字段准确率、审核效率、成本、客户用量。

08重点风险与注意点

不要只存抽取结果，要存证据。
每个字段应记录来源页码、坐标、原始文本、模型版本、置信度、修正记录。否则后续无法审计，也无法提升人工审核效率。
低置信结果必须进人工闭环。
单据识别是业务系统，不是 Demo。真实环境一定有模糊扫描件、手写、盖章遮挡、错页、重复上传。
字段 schema 要稳定，模型输出要受约束。
LLM/VLM 输出必须走 JSON Schema 校验和后处理，不要直接信自然语言输出。
多租户隔离从第一天做。
文件、任务、配置、模型权限、日志查询都要带 tenant_id；对象存储路径和加密 Key 也要隔离。
把成本看成架构约束。
VLM/LLM 很强，但不应每张单都跑。用分类器和置信度路由，把重模型用在真正复杂或低置信场景。

09MVP 到规模化路线

1

MVP：跑通 2-3 类高价值单据

上传、异步任务、OCR/VLM 抽取、人工审核、结构化导出、基础后台。

2

平台化：模板与规则配置

把字段 schema、阈值、规则、审核流程放进后台，减少新增单据类型的开发成本。

3

规模化：多租户与模型治理

租户隔离、计费、模型灰度、评测集、自动监控、SLA 和成本治理。

4

智能化：反馈闭环与主动质检

人工修正数据回流，字段级 drift 监控，自动发现模板失效和异常供应商。

我建议的落地优先级

先选一个业务闭环最清晰的场景，比如报销发票/采购单/物流单。不要一开始覆盖所有单据类型；先把“上传 → 抽取 → 审核 → 回写业务系统 → 指标看板”闭环做扎实。

技术栈上，前端可用 React/Vue + 管理台组件库；后端推荐 Java/Spring Boot 或 Python/FastAPI 按团队能力选；任务编排和模型服务建议独立服务化，避免和业务后台耦合。

North Star Metrics: 字段级准确率 / 自动通过率 / 平均处理时长 / 人工修改率 / 单据处理成本
