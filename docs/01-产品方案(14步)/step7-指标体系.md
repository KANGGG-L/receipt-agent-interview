## 1. 北极星指标定义与拆解（North Star Metric）

```
                   ┌──────────────────────────────────────────────────────────┐
                   │             receipt_agent 北极星指标（North Star）        │
                   └──────────────────────────────────────────────────────────┘
                                                │
         ┌──────────────────────────────────────┴──────────────────────────────────────┐
         ▼                                                                             ▼
  【北极星指标名称】                                                            【核心计算公式】
  每周每店成功极速核对入库的单据数                                               Weekly Verified Receipts per Active Store
  (Weekly Verified Receipts / Active Store)                                     = Σ (status='approved' 且有效写入台账单据)
  ──────────────────────────────────────                                        ─────────────────────────────────────────
  目标值：≥ 50 ~ 80 张 / 周 / 店（覆盖 85%+ 进货）                              天然内建“AI 提取质量 + 人工背书采纳”双重门槛
```

### 1.1 为什么选择该指标作为北极星？
1. **真实反映用户核心价值**：单据只有经过“识别 → 算术门禁 → 左右核对 → 老板 Approve 审批入库”，才意味着完成了一次完整的数据流转，切实为餐厅节省了手工录入与对账时间；
2. **天然过滤虚荣指标（Anti-Vanity Metric）**：纯粹的“上传量（Upload Count）”或“注册用户数”是典型的虚荣指标（上传后若识别混乱、用户直接弃用并不产生价值）。必须以 `Approve 审批入库` 为终态，内建质量与业务采纳门槛；
3. **SaaS 续费与商业健康的先验信号**：周均入库单据数直接衡量单店的使用深度（Depth of Usage）。每周稳定入库 >50 张的商户，月留存率达 95%+；入库量下滑是商户流失的最早期预警信号。

### 1.2 北极星指标一级与二级拆解树

```
                     北极星：每周每店成功入库单据数（张/周/店）
                                       │
        ┌──────────────────────────────┼──────────────────────────────┐
        ▼                              ▼                              ▼
  【1. 采集与漏斗层】            【2. 算法与质量层】            【3. 审批与采纳层】
  · 活跃商户周上传天数           · 字段级严格 F1 分数           · 待审批单据处理率
  · 批量上传使用渗透率           · 单据一次通过率 Pass@1        · 无修改一键 Approve 率
  · 失败转手工兜底率             · 字段编辑率 (FER ≤10%)        · 平均复核耗时 (≤30s)
```

## 2. AI 产品多层指标金字塔（Metrics Pyramid）

围绕“体验、算法、业务、成本”四个维度，搭建纵深分层的指标金字塔：

```
                                  ┌───────────────────────────┐
                                  │       L4 商业与业务层     │
                                  │   WAU 留存 / 续费 / 转化  │
                                  ├───────────────────────────┤
                                  │       L3 体验与交互层     │
                                  │   复核耗时 / FER / 满意度 │
                                  ├───────────────────────────┤
                                  │       L2 模型与算法层     │
                                  │   解析率 / 字段 F1 / 门禁 │
                                  ├───────────────────────────┤
                                  │       L1 成本与系统层     │
                                  │   Token 成本 / 延迟 / SLA │
                                  └───────────────────────────┘
```

### 2.1 四层指标详细定义表

| 指标层级 | 指标名称 (Metric Name) | 口径定义与计算逻辑 | 数据来源 / 埋点 | 业务意义与目标导向 |
|:---|:---|:---|:---|:---|
| **L3 体验层** | **单张单据复核耗时** | 用户在 Side-by-Side 页面打开至点击提交的中位时长 (P50/P90) | 客户端埋点 `review_submit` | 验证是否达到“不到 1 分钟”承诺（目标 ≤30s）。 |
| | **字段编辑率 (FER)** | $\text{FER} = \frac{\text{用户人工修改字段数}}{\text{单据总字段数}}$ | 服务端 `field_edited` | 衡量 AI 预填有效性；FER 越低，人工心智负担越小。 |
| | **零修改通过率 (Zero-Edit Rate)** | 用户未做任何字段改动直接点击 Approve 的单据占比 | 状态机日志 | 衡量 AI 端到端直识免修率（目标 ≥70%）。 |
| | **一次通过率 (Pass@1)** | 首轮多模态 VLM 识别即通过契约与算术门禁的比例 | `ocr_parsed` | 衡量首轮解析质量，避免进入重试耗时。 |
| **L2 算法层** | **单据解析合法率** | 产出符合 Pydantic 强契约 JSON 结构的单据比例 | 服务端契约校验 | 衡量大模型输出遵循格式能力（硬红线 100%）。 |
| | **关键字段级 F1 (金额/数量)** | 数量、单价、总额与真实 Ground Truth 匹配的加权 F1 | 评测台 Golden GT | 财务核心字段必须极高精度（硬红线 ≥95%）。 |
| | **普通字段级 F1 (品名/规格)** | 品名、俗称与真实 Ground Truth 匹配的加权 F1 | 评测台 Golden GT | 允许小范围别名容错（目标 ≥85%）。 |
| | **算术守恒门禁拦截率** | 发现 `数量×单价≠金额` 并成功拦截修正的比例 | 算术门禁引擎 | 100% 绝对拦截大模型计算幻觉。 |
| **L4 业务层** | **活跃商户周留存率 (WAU Ret)** | 第 W 周活跃（有 Approve）的商户在第 W+1 周仍活跃的比例 | 用户行为日志 | 检验产品是否成为后厨日常刚需习惯（目标 ≥75%）。 |
| | **月结对账差异发现率** | 自动比对发现“漏单/错价/多收”并被商户采纳的比例 | 对账引擎日志 | 验证财务对账商业闭环的价值转化。 |
| | **价格偷涨预警命中率** | 成功捕捉单品涨幅 >10% 并促成商户查看的比例 | 价格异动引擎 | 创造极高 Aha Moment，守住餐厅毛利。 |
| **L1 成本层** | **单张单据综合 Token 成本** | 单张单据全流程消耗的 API 费用总和 | 计费日志 | 确保高毛利 UE 模型成立（控制在 ≤HK$0.03/张）。 |
| | **端到端解析延迟 P95** | 从图片上传完成到返回结构化结果的 95 分位耗时 | 服务端耗时监控 | 避免用户在移动端长时间转圈等待（目标 ≤12s）。 |
| | **系统高可用性 (SLA)** | API 服务无故障正常运行时间占比 | 运维监控 | 保障清晨 6:00 采购高峰稳定可用（目标 99.9%）。 |

## 4. 全生命周期埋点设计规范（Event Tracking Specification）

严格遵循服务端 API-first 埋点原则，定义覆盖“采集 → 识别 → 校验 → 复核 → 审批 → 财务”全生命周期的 11 个标准行为事件：

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        11 个核心业务生命周期埋点事件流                                 │
├────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                        │
│   【采集】receipt_uploaded ──► 【识别】ocr_parse_started ──► ocr_parsed / ocr_error    │
│                                                                       │                │
│   【核对】receipt_review_submitted ◄── field_edited ◄── math_guard_checked            │
│          │                                                                             │
│          ▼                                                                             │
│   【审批】receipt_approved (北极星) / receipt_flagged ──► price_anomaly_flagged         │
│          │                                                                             │
│          ▼                                                                             │
│   【财务】reconciliation_completed (月结对账完成)                                      │
│                                                                                        │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 11 个关键事件详细规范定义表

| # | 事件名称 (Event Name) | 触发时机 | 公共上下文参数 (Common Context) | 专属业务 Payload 字段定义 | 支撑的核心指标 |
|:---:|:---|:---|:---|:---|:---|
| **1** | `receipt_uploaded` | 移动端单张/批量单据上传成功 | `tenant_id`, `account_id`, `device_os`, `timestamp` | `batch_id`, `batch_size`, `upload_source` (camera/album), `file_size_kb` | 漏斗起点、批量渗透率 |
| **2** | `ocr_parse_started` | 后端 Worker 从 Job 队列取出单据启动解析 | 同上 | `receipt_id`, `retry_attempt` (1/2), `selected_engine` (openai/qwen) | 队列排队延迟 |
| **3** | `ocr_parsed` | 多模态 VLM 提取完成并生成结构化草稿 | 同上 | `receipt_id`, `doc_form`, `duration_ms`, `tokens_used`, `cost_hkd`, `pass_at_1` | 算法准确率、Token 成本、P95 延迟 |
| **4** | `ocr_error` | VLM 解析崩溃、超时或契约校验彻底失败 | 同上 | `receipt_id`, `error_type` (timeout/format/schema), `fallback_engine` | 系统故障率、降级触发率 |
| **5** | `math_guard_checked` | 代码层算术守恒校验执行完毕 | 同上 | `receipt_id`, `is_arithmetic_valid` (bool), `delta_amount`, `auto_fixed` (bool) | 门禁拦截率、算术自洽率 |
| **6** | `field_edited` | 用户在 Side-by-Side 界面修改某字段内容 | 同上 | `receipt_id`, `field_name` (price/qty/name), `old_val`, `new_val`, `edit_seq` | 字段级 FER、高频错误字段定位 |
| **7** | `receipt_review_submitted`| 店员/老板完成人工复核并点击保存提交 | 同上 | `receipt_id`, `review_duration_s`, `total_fields`, `edited_fields_count`, `fer_rate` | **单张复核耗时**、**FER** |
| **8** | `receipt_approved` | 老板点击 Approve 批准单据，幂等写入台账 | 同上 | `receipt_id`, `total_amount`, `items_count`, `payment_mark`, `is_idempotent` | ** 北极星指标（入库单数）** |
| **9** | `receipt_flagged` | 老板或财务标记单据异常并驳回 | 同上 | `receipt_id`, `flag_reason` (blurred/wrong_supplier/fake), `supplier_name` | 异常率、供应商信用扣分 |
| **10**| `price_anomaly_flagged`| 系统检测到单品涨幅 >10% 触发告警标红 | 同上 | `receipt_id`, `sku_id`, `sku_name`, `historical_avg_price`, `current_price`, `surge_pct` | 价格异动预警量、毛利防漏 |
| **11**| `reconciliation_completed`| 上传供应商月结单，对账引擎完成四向对齐 | 同上 | `statement_id`, `supplier_id`, `total_receipts_matched`, `discrepancy_count`, `delta_total` | 对账耗时压缩率、差异发现率 |
