## 一、探索背景与目标

本项目是一个面向复杂发票单据的多模态智能体提取、校验与反思审计系统。系统支持多种异构大模型（如 DeepSeek-V3/R1/V4.1-Flash、OpenAI GPT-4o/o1/o3-mini、Qwen-VL 等各类视觉与纯文本模型），并在业务层落地了“常规主引擎”与“灰度切流引擎”双轨运行机制（覆盖识别、审核、解析共 6 个引擎腿）。

然而，随着系统快速迭代，代码库中逐渐积累了参数定义与表现不一致、前端配置卡片缺乏统一组件化抽象、各引擎高级工程超参及周边控件各自为政、前后端参数边界模糊等系统性架构债务。

你需要跳出单一文件或局部的视线限制，深入整个代码库的各个子系统，系统性探查各层模块的物理实现与逻辑关联。

## 二、Codebase 全局探索维度与排查指引

### 1. 引擎配置与数据契约层 (`demo/app/engine_config.py`, `demo/app/models.py`, `demo/app/db.py`, `demo/app/api_admin.py`)
- **配置模型契约**：
  - 全面审查 `EngineConfig` 与 `EngineConfigBody` 的 Pydantic 字段定义，梳理常规三腿（`rec`, `aud`, `parse`）与灰测三腿（`grey_rec`, `grey_aud`, `grey_parse`）的全部参数字段与类型约束；
  - 检查各参数的合法范围、默认值体系与校验器（如 `clamp_temperature`, `clamp_max_tokens`, `clamp_image_detail`, `clamp_max_retry_rounds` 等）；
  - 分析 `extra="forbid"` 强类型机制对未知/非标参数的拦截规则。
- **持久化与接口事务**：
  - 探查配置加载（`GET /api/admin/engine-config`）与更新（`PUT /api/admin/engine-config`）的完整时序与持久化机制；
  - 探查预设模版（Presets）、自定义网关与历史版本回滚在数据库（SQLite `app_settings` 表）中的存储与序列化方案。

### 2. LLM 统一网关与多模态协议层 (`demo/app/llm.py`, `demo/app/services/`)
- **多模态协议适配**：
  - 探查多模态视觉请求在底层如何组装为标准 OpenAI Wire 协议（如 `_lc_to_openai`），包括 Base64 编码方式、PIL 限边防爆（`_MAX_IMAGE_SIDE`）及 `image_url.detail`（`high`/`auto`/`low`）的下发规则；
  - 检查纯文本模型与多模态视觉模型在请求体组装上的模态分支处理。
- **多模型差异防御与自适应自愈机制**：
  - 深入排查系统针对不同模型家族（DeepSeek 官方 API、OpenAI o1/o3 推理模型、常规多模态等）在 Layer 1 静态前置自适应（如 `reasoning_effort` 剥离、`max_tokens` 钳制至 8192、`max_completion_tokens` 键名桥接、`temperature` 剥离）上的具体实现；
  - 深入排查 Layer 2 动态 400 参数剥离自愈算法，分析错误特征签名库、单请求就地重试控制（防死循环上限）及可观测性元数据（`adapted_params`）的流转沉淀机制。

### 3. 多智能体业务流转与容灾调度层 (`demo/app/chains/`, `demo/app/services.py`)
- **Agent 工作流协作**：
  - 探查 Supervisor（总控编排）、ExtractChain（多模态视觉识别）、AuditChain（规则与反思审核）、ParseChain（Schema 结构化自愈）四者之间的数据流转与契约约定；
  - 检查不同引擎腿在业务层消费的参数集（如审核腿为何强制 `temperature=0.0`，解析腿为何仅处理纯文本）。
- **容灾、重试与短路控制**：
  - 梳理重试轮数（`max_retry_rounds`）、超时控制（`timeout_seconds`）在业务调度层的真实执行路径；
  - 探查四大短路保护（确定性错误 400/401 短路、输出格式质量单轮短路、规则门禁快速反馈）的具体判定逻辑。
- **灰度分流与流量路由**：
  - 探查 `grey_enabled`、`grey_percent`、`grey_assign_mode` 在调度层如何执行单据随机分流与商户 MD5 哈希一致性分流。

### 4. 前端视图、渲染与交互组件层 (`demo/templates/`, `demo/static/`)
- **模板与视图组织 (`demo/templates/index.html`)**：
  - 全局扫描前端模板中「系统与引擎配置」（`section#tab-engine`）的 DOM 组织架构，包括常规三腿子视图（`#engineSubView_01`）与灰测三腿子视图（`#engineSubView_02`）；
  - 对比全部 6 个引擎卡片的 DOM 结构，剖析为何常规卡片与灰测卡片存在结构差异（例如：常规识别具备高级 Combobox 与 Header 工具栏，其余卡片仍为原生 `<select>` 且测试按钮侵入表单网格；审核/解析卡片删除切片粒度导致 2x2 网格坍塌与右侧悬空留白；灰测审核卡片遗漏确定性 0.0 锁定提示等）；
  - 评估 1200+ 行静态重复 HTML 的代码冗余度，设计统一 Jinja2 Macro 单点模板源的可行性。
- **前端交互脚本与生命周期 (`demo/static/js/main.js`)**：
  - 梳理配置数据双向绑定机制（加载回填、表单采集、提交持久化）；
  - 检查高级参数折叠展开联动、标题栏 Badge 四段式格式化、模型特性即时提示（`updateModelTraitHints`）、实时成本测算器（`updateEngineCostCalculator`）与引擎联通性测试（`probeSingleEngineLeg`）的事件链路；
  - 分析是否存在过度依赖硬编码 ID 的多分支结构，评估通过 `[data-engine-leg]` 实现统一事件委托与组件化解耦的改造方案。

### 5. 评测数据集与 Ground Truth 体系 (`demo/evalsets/`)
- 检查评测集清单（`manifest.csv`）与真实票据图像（`receipts/`）；
- 梳理评测模型（如 `deepseek-v4.1-flash` 作为 Ground Truth）对多模态参数的具体要求与基准指标。

### 6. 自动化测试套件与契约边界 (`demo/tests/`, `tests/`)
- 检索全量自动化测试文件（包括 `test_advanced_engine_params.py`, `test_model_adaptive_params.py`, `test_upstream_error_classification.py`, `test_image_detail_localization.py` 等）；
- 列出测试用例强依赖的 DOM 选择器与 API 契约断言，明确系统在统一化重构时的绝对兼容底线（Zero Regression）。
