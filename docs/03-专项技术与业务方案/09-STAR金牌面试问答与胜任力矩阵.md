# 09 · STAR 金牌面试问答与胜任力速查卡

> 本文档专为 **高频技术面试与产品业务深挖** 准备，按照标准 **STAR 结构（情境 Situation · 任务 Task · 行动 Action · 结果 Result）** 提炼核心答辩逻辑。

---

### Q1：请简要介绍一下你在 PGM 的这段项目经历，为什么要做这个收据 Agent？

- **S (情境)**：香港餐饮面临“招工难、老龄化、净利润率仅 5%~8%”的残酷现实。餐厅每天清晨收到大量沾满油污的街市手写单、印章单。传统 ERP（如 Foodival）依赖电子采购单，竞品（Air Purchase）只做单点 OCR 录入导致前后端数据孤岛。
- **T (任务)**：作为子模块产品负责人，我的目标是从 0 到 1 打造一套让后厨店员“拍照即可预填、几十秒核对入库”的智能中台，打通进销存一体化，实时核算菜品毛利。
- **A (行动)**：
  1. 深入 12 家香港食肆跟单，梳理出 7 种单据形态与司马斤等本土计量规则；
  2. 撰写 14 步标准大厂 PRD，设计 Side-by-Side 对照交互与确定性算术门禁；
  3. 推动 5 阶段敏捷研发与三方对抗评审。
- **R (结果)**：覆盖 17 个落地业务场景，识别成功率达 100%，单张成本仅 2.4 港仙，产品终验得分 4.92/5.0。

### Q2：为什么你们最终选择了多模态 VLM，而不是传统的 OCR+LLM（看想分离）？

- **S (情境)**：在技术选型初期，团队对于使用传统 OCR（Tesseract/PaddleOCR）、商业云 OCR 还是多模态大模型存在争议。
- **T (任务)**：需要通过科学的量化实验论证最优技术路径，兼顾识别率、耗时与 API 成本。
- **A (行动)**：
  1. 搭建统一评测台（Runner）与独立标注系统（FastAPI 15001），构建了 L0 到 L9 共 10 级技术选型阶梯；
  2. 针对 163 张真实香港单据进行全量横向 Benchmark；
  3. 实验发现：L0 传统 OCR 成功率仅 3.1%；L7“看想分离”仅 26.4%（OCR 专有读图丢弃了表格空间相对位置与印章视觉语义）；而 L4 多模态直识达到 100%。
- **R (结果)**：最终定稿采用 `qwen3-vl-flash` 作为生产主力，以单张 ¥0.0022（2.4 港仙）的极低成本实现 100% 成功率，单月单店成本不足 HK$ 1.00。

### Q3：AI 必然存在幻觉和识别错误，如何保证财务与库存数据 100% 准确？

- **S (情境)**：进货单据直接关联库存台账与对账付款，一旦发生“小计或单价算错”，将直接造成经济损失。
- **T (任务)**：在产品架构与交互设计上建立不可击穿的防幻觉安全防线。
- **A (行动)**：
  1. **架构层（三层互不信任）**：AI 只做提取与置信度上报；核心算术（$\text{单价} \times \text{数量} = \text{金额}$ 与总计求和）由确定性代码引擎校验，门禁先于入库；
  2. **交互层（Human-in-the-Loop）**：设计 Side-by-Side 左右对照界面，异常字段高亮标红并附带自然语言理由，必须经人工审核（Approve）才触发唯一的台账写入点；
  3. **数据层（Append-Only 台账）**：库存流水只增不改，修改只产生冲销事件，全链路保留 5 元组审计日志。
- **R (结果)**：线上未发生任何静默算术错误，审核采纳率与用户信任度保持在 95% 以上。

### Q4：多租户 SaaS 架构下，如何杜绝不同门店之间的供应商协议价和账目数据穿透？

- **S (情境)**：不同餐厅拥有各自的进货底价与私有供应商关系，严禁 A 门店通过 AI 检索或模型记忆看到 B 门店的数据。
- **T (任务)**：设计一套软硬件结合的防穿透数据隔离规范。
- **A (行动)**：设计并落地**四层隔离沙箱架构**：
  1. **零系统上下文沙箱**：下发给 VLM 的提示词中严格剥离任何系统环境、用户信息与汇总账目；
  2. **Chroma 租户硬隔离 RAG**：向量检索强制注入 `{"$and": [{"tenant_id": Tid}]}` 物理过滤，跨租户向量零命中；
  3. **最小权限数据投影**：审核 Agent 仅下发当前单据字段与本店同物料均价；
  4. **反向渗透白名单过滤器**：Pydantic 契约白名单过滤非 Schema 字段，阻断敏感关键词。
- **R (结果)**：通过越权矩阵回归测试（`test_tenant_overreach_matrix.py`），跨租户数据泄漏零风险。

### Q5：你们是如何衡量 AI 模块的业务价值与设计 A/B 实验的？

- **S (情境)**：模型和 Prompt 调优不能靠主观感觉，必须有客观的数据实验与业务指标衡量。
- **T (任务)**：搭建一套大厂标准的 AI 产品体验指标体系与统计学实验框架。
- **A (行动)**：
  1. **五大指标体系**：定义了【模型提取准确率】、【字段幻觉率】、【人工编辑修正率】、【审核理由采纳率】和【用户信任度评分】；
  2. **五步漏斗追踪**：采集 `上传 -> 预填 -> 编辑 -> 审核 -> 入账` 转化漏斗；
  3. **A/B 实验 z 检验门禁**：设立 control 与 treatment 分组，通过**双比例双尾 z 检验**计算 p-value，强制设定最小样本量，杜绝小样本假阳性盲目推全。
- **R (结果)**：新版 Prompt 调优实现了准确率提升 20%、人工修正率下降 20%（$p < 0.05$ 显著），数据驱动闭环跑通。

### Q6：实施过程中遇到的最难排查的一个 bug 是什么？怎么解决的？

- **S (情境)**：在阶段 0 脱敏视图实测中，一张同时含有 11 位手机号和 18 位身份证的单据发生脱敏异常。
- **T (任务)**：必须保证脱敏后的掩码与原字符长度严格 1:1，且不能发生正则误吃。
- **A (行动)**：
  1. **问题根因定位**：开发最初使用的手机号正则优先匹配了 18 位身份证中间的 11 位生日段，导致身份证被截断为残缺形态；
  2. **对抗审查拦截**：对抗 Reviewer 在代码审查阶段精准拦截并标记为 P0 缺陷；
  3. **解决方案**：引入 `\b` 单词边界，重构正则执行优先级（18 位身份证全局优先匹配，手机号次之），并在活体服务器上构造包含双字段的真实单据回归验证。
- **R (结果)**：实现了手机号（前3后4）与身份证（前6后4）精准无损掩码，顺利通过三方对抗终验。
