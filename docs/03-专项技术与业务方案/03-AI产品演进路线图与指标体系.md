## 阶段总览与依赖

```
阶段 0 (安全底座) ──┐
                   ├─→ 阶段 1 (AI 可见性) ──→ 阶段 2 (A/B 度量) ──┐
                   │                                              ├─→ 阶段 4 (Agent 前沿)
                   └─→ 阶段 3 (供应商深度) ────────────────────────┘
```

- **阶段 0 必须先做**：没有审计日志和 approve 闸门，后续所有 AI 改动都无法度量与追责。
- **阶段 1、3 可并行**：前端体验组与后端数据组分别推进。
- **阶段 2 依赖 1**：指标体系需要 `use_grey` 持久化和审核采纳率记录先就位。
- **阶段 4 最后做**：依赖前面的指标和供应商数据，否则 Agent 没数据可推理。

| 阶段 | 周期 | 负责 | 核心交付 |
|------|------|------|----------|
| 0 安全底座 | 1-2 周 | 后端 | approve 闸门 / 审计日志 / 脱敏视图 / 软删除 |
| 1 AI 可见性 | 2 周 | 前端+AI | 审核解释 / 对照 UI / 灰测标记 / 主动推荐 |
| 2 A/B 度量 | 2-3 周 | 数据 | 指标体系 / 效果对比 / 漏斗 / 快照完整化 |
| 3 供应商深度 | 2-3 周 | 后端+前端 | 供应商详情页 / allowlist 灰测 / 双边对账 / 加权成本 |
| 4 Agent 前沿 | 3-4 周 | AI | 对话查询 / 多步推理 / RAG / 质量预检 / 生成式 UI |

## 阶段 0｜安全底座（1-2 周）

**目标**：堵住财务写操作与数据安全的最低底线。不动 AI 能力，只补"出问题能追责、能恢复"。

### 交付物

| # | 交付物 | 涉及文件 |
|---|--------|----------|
| 0.1 | approve 加 status 校验：仅 `edited` 状态可 approve | `demo/app/api_receipts.py:261` |
| 0.2 | `audit_logs_json` 真实写入：每次 approve/save_edited/flag/discard/promote/set_engine_config 记 who/what/old/new/timestamp | `demo/app/db.py` + 所有写端点 |
| 0.3 | 脱敏视图：`GET /api/receipts?desensitized=true` 对 `raw_llm`/付款标记/人名/联系方式掩码 | `demo/app/api_receipts.py` 新增参数 |
| 0.4 | discard 改软删除（`deleted_at`），加回收站 | `demo/app/db.py:235` |

### 验收标准

1. 非 `edited` 状态单据调 approve → HTTP 409 + 错误码 `INVALID_STATUS`
2. 任意一次写操作后，`audit_logs_json` 含完整 5 元组（who/what/field/old/new/timestamp）
3. `?desensitized=true` 返回的 `raw_llm` 中手机号/身份证/金额关键字段被掩码，原值不可见
4. 删除的单据在回收站可 30 天内恢复

### 测试方法与预期结果

```text
1. POST /api/receipt/{id}/approve 其中 status='parsed'
   → 期望 409，body.code='INVALID_STATUS'

2. 修改一张单据单价 5→8 后 approve
   → 查 receipt.audit_logs_json 期望含
     {who, field:'unit_price', old:5, new:8, ts}

3. GET /api/receipts?desensitized=true
   → 断言 raw_llm 不含 '13' 开头 11 位手机号正则匹配
   → 断言付款标记/人名被掩码

4. DELETE /api/receipt/{id} 后 GET /api/admin/trash
   → 期望该单可见，POST restore 后回到归档
```

## AI 产品体验指标体系

> 阶段 2 的完整规格。把"准确率/幻觉率/信任度"从口号变成可建表、可采集、可查询、可告警的系统。

### 指标精确定义

| 指标 | 公式 | 分子来源 | 分母来源 | 粒度 | 时间窗 |
|------|------|----------|----------|------|--------|
| **识别准确率** | `1 - 修改字段数/总字段数` | `ai_decision_log` 中 `ai_value != user_value` 的字段数 | 单据总字段数（5 字段 × items） | 单据→供应商/引擎/模型/全局 | 日/周/月 |
| **幻觉率** | `幻觉字段数/总字段数` | 商品名不在供应商历史库 / 单价偏离历史均值 >50% / 数量异常 | 总字段数 | 同上 | 同上 |
| **人工修正率** | `用户修改字段数/总字段数` | 用户改过的字段数 | 总字段数 | 同上 | 同上 |
| **审核采纳率** | `adopted/(adopted+dismissed+overridden)` | `ai_decision_log` 中 `decision_type=audit` 按 adopted 取值 | 同左分母 | 同上 | 同上 |
| **用户信任度** | `连续接受建议的决策数/总决策数` | sliding window 内 `adopted=true` 计数 | 窗口内总决策数 | 账号/全局 | 滑窗 50 次 |
| **置信度校准** | `高置信段准确率 - 高置信段占比` | confidence 分桶 vs 实际准确率 | — | 模型 | 周 |

> **准确率 vs 修正率的区别**：准确率看"AI 对不对"，修正率看"用户改没改"。用户可能把对的改成错的（修正率↑但准确率↓），也可能把错的改成对的（两个都受益）。两个指标交叉看才能判断 AI 质量。

### 存储模型

```sql
-- 每次 AI 决策一行（识别/审核/解析/复盘各阶段都写）
CREATE TABLE ai_decision_log (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  ts           TEXT NOT NULL,              -- ISO 时间
  receipt_id   INTEGER NOT NULL,
  supplier_id  INTEGER,
  experiment_id INTEGER,                   -- 归属哪个实验（可空=常规生产）
  grp          TEXT NOT NULL,              -- 'control'|'treatment'（常规/灰测）
  engine       TEXT NOT NULL,
  model        TEXT NOT NULL,
  use_grey     INTEGER NOT NULL,           -- 0/1，冗余便于查询
  decision_type TEXT NOT NULL,             -- 'extract'|'parse'|'audit'|'review'
  field_path   TEXT NOT NULL,              -- 'items[0].unit_price'
  ai_value     TEXT,                       -- AI 给的值（JSON 序列化）
  user_value   TEXT,                       -- 用户最终确认值（approve 时回填，初始 NULL）
  adopted      INTEGER,                    -- 0/1/NULL（NULL=未决策）
  confidence   REAL,                       -- AI 置信度
  is_hallucination INTEGER,               -- 0/1/NULL（幻觉判定，approve 后回填）
  extra        TEXT                        -- JSONB 兜底
);
CREATE INDEX idx_dec_grp_ts ON ai_decision_log(grp, ts);
CREATE INDEX idx_dec_supplier ON ai_decision_log(supplier_id, ts);

-- 定时聚合快照（每小时跑一次，避免仪表盘现算全表）
CREATE TABLE ai_metric_snapshot (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  period_start  TEXT NOT NULL,
  period_end    TEXT NOT NULL,
  granularity   TEXT NOT NULL,             -- 'global'|'supplier'|'engine'|'model'|'experiment'
  granularity_id TEXT,                   -- 对应 supplier_id / engine / model / experiment_id
  grp           TEXT,                      -- control/treatment（实验对比用）
  accuracy              REAL,
  hallucination_rate    REAL,
  edit_rate             REAL,
  audit_adoption_rate   REAL,
  trust_score           REAL,
  sample_size           INTEGER,           -- 样本量（<30 时仪表盘标灰，不可信）
  computed_at           TEXT NOT NULL
);
```

### 采集点

| 阶段 | 写入位置 | 写什么 |
|------|----------|--------|
| 识别完成 | `supervisor.py` 识别后 | `decision_type=extract`，每 item 每字段一行，`ai_value` 填识别值，`user_value=NULL` |
| 用户编辑 | `api_receipts.py:save_edited` | 回填 `user_value`（用户改了什么），此时可判 `adopted` |
| approve | `api_receipts.py:approve_receipt` | 最终确认值落库，触发幻觉判定（查供应商历史库），写 `is_hallucination` |
| 审核 | `chains/audit_chain.py` | `decision_type=audit`，`ai_value` 填异常标记，`user_value` 在用户处置后回填 |
| 复盘 | `chains/review_chain.py` | `decision_type=review`，AI 建议 vs 用户是否采纳 |

> 关键：**采纳判定必须在 approve 时回填**，不能在 save_edited 时，因为用户可能改了又改。approve 才是终态。

### 查询端点

```
GET /api/admin/ai-metrics
  ?metric=accuracy,hallucination,edit_rate,trust
  &granularity=supplier|engine|model|experiment|global
  &group=control|treatment|both
  &period=7d|30d|custom&from=&to=
  &supplier_id=&engine=&model=&experiment_id=
```

返回：时间序列 + 当前值 + 样本量 + 置信区间（样本<30 标灰）。

```text
│ ↑+3pp    │ ↓-0.5pp  │ ↑+1pp    │ ↓-6pp 跌破阈值 │
├──────────┴──────────┴──────────┴───────────────┤
│ 准确率趋势线（常规 vs 灰测双线）                  │
├──────────────────────────────────────────────────┤
│ 置信度校准图：AI 自报置信度 vs 实际准确率          │
│ （理想=y=x，偏离=过度自信/不够自信）               │
├──────────────────────────────────────────────────┤
│ 幻觉 TOP 字段：商品名幻觉 12 例 / 单价幻觉 5 例    │
└──────────────────────────────────────────────────┘
```

### 告警阈值

| 指标 | 告警条件 | 级别 |
|------|----------|------|
| 信任度 | sliding window <70% | [ALERT]  信任塌方，暂停灰测 |
| 准确率 | 周环比跌 >5pp | [WARN]  调查模型回退 |
| 幻觉率 | 单供应商幻觉率 >10% | [WARN]  该供应商需补 VendorMemory |
| 审核采纳率 | <30%（AI 标的异常用户 70% 忽略） | [WARN]  AI 审核过度敏感，调阈值 |
| 样本量 | <30 |  数据不足，不告警只标灰 |

## 数据实验框架（A/B + 行为 + 漏斗）

> 阶段 2 的另一半规格。把"A/B 测试、用户行为分析、AI 使用漏斗"落地为可建表、可查询、可显著判定的系统。

### A/B 实验生命周期

```text
 hypothes → 创建 → 运行 → 分析 → 结论(promote/rollback/inconclusive)
   ↑                                              │
   └────────── 结论归档，可复盘 ─────────────────┘
```

### 实验存储模型

```sql
CREATE TABLE experiment (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  name          TEXT NOT NULL,
  hypothesis    TEXT NOT NULL,             -- "新模型 mimo-v3 准确率 +5pp"
  success_metric TEXT NOT NULL,           -- 'accuracy' 主指标
  guardrail_metrics TEXT,                 -- JSON ['trust','hallucination'] 护栏指标
  status        TEXT NOT NULL,            -- 'draft'|'running'|'stopped'|'concluded'
  grey_snapshot TEXT NOT NULL,            -- 灰测组配置快照 JSON
  target_percent INTEGER,
  target_supplier_ids TEXT,               -- JSON [3,7] allowlist
  start_ts      TEXT,
  end_ts        TEXT,
  min_sample    INTEGER DEFAULT 100,      -- 最小样本量，未达不结题
  conclusion    TEXT,                      -- 'promote'|'rollback'|'inconclusive'
  conclusion_reason TEXT,
  concluded_by  TEXT,
  concluded_at  TEXT
);

CREATE TABLE experiment_assignment (
  experiment_id INTEGER NOT NULL,
  receipt_id    INTEGER NOT NULL,
  grp           TEXT NOT NULL,            -- 'control'|'treatment'
  assigned_at   TEXT NOT NULL,
  PRIMARY KEY (experiment_id, receipt_id)
);
```

### 实验端点

```
POST   /api/admin/experiments            创建实验（状态=draft）
POST   /api/admin/experiments/{id}/start  开始运行（status=running，记录 start_ts）
GET    /api/admin/experiments            列表（含实时指标）
GET    /api/admin/experiments/{id}       详情（含分组指标对比 + 显著性）
POST   /api/admin/experiments/{id}/conclude  结论（必须附 reason，自动校验 min_sample）
```

### 显著性判定（避免假阳性）

- 主指标 `success_metric` 用双比例 z 检验
- 要求 `p < 0.05` 且 **效应量 > 最小可检测效应（MDE）** 才允许 `promote`
- 样本量 < `min_sample` 时端点拒绝结题，返回 `INSUFFICIENT_SAMPLE`
- 护栏指标任一恶化超阈值 → 禁止 promote，即使主指标显著

### 行为事件模型

```sql
CREATE TABLE user_event (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  ts          TEXT NOT NULL,
  account_id  TEXT,
  session_id  TEXT NOT NULL,
  event_type  TEXT NOT NULL,
  receipt_id  INTEGER,
  properties  TEXT,                      -- JSONB
  grp         TEXT                       -- 归属实验分组（便于漏斗分组对比）
);
CREATE INDEX idx_evt_type_ts ON user_event(event_type, ts);
CREATE INDEX idx_evt_session ON user_event(session_id);
```

**事件清单**（在对应代码点埋点）：

| event_type | 埋点位置 | properties |
|------------|----------|------------|
| `upload` | `api_receipts.py:upload_batch` | `{file_count}` |
| `parse_start` | supervisor 识别前 | `{engine,model,grp}` |
| `parse_done` | 识别后 | `{duration_ms, confidence}` |
| `parse_error` | 识别失败 | `{error_type}` |
| `edit` | `save_edited` | `{fields_changed}` |
| `audit_flag` | `flag_receipt` | `{reason}` |
| `approve` | `approve_receipt` | `{turnaround_min}` |
| `ai_suggestion_shown` | 对照 UI 展示 | `{field}` |
| `ai_suggestion_adopted` | 用户采纳 | `{field,ai_value,user_value}` |

### 漏斗定义与查询

漏斗配置（可配，非写死）：

```json
{
  "name": "上传到入库主漏斗",
  "steps": [
    {"event": "upload",            "label": "上传"},
    {"event": "parse_done",        "label": "解析成功"},
    {"event": "edit",              "label": "编辑"},
    {"event": "audit_flag",        "label": "审核", "optional": true},
    {"event": "approve",           "label": "审批"},
    {"event": "inventory_in",      "label": "入库"}
  ],
  "window_minutes": 1440
}
```

查询端点：

```
GET /api/admin/funnel?name=upload_to_inventory&group=control,treatment&period=7d
```

返回每步：绝对数、转化率、累计转化率、中位耗时、与对比组的差异。

### 漏斗仪表盘

```text
┌─────────────────────────────────────────────┐
│ 上传到入库主漏斗  时间窗[7天]  分组[常规+灰测] │
├──────┬────────┬────────┬────────┬───────────┤
│ 步骤  │ 常规    │ 灰测    │ 差异    │ 中位耗时   │
├──────┼────────┼────────┼────────┼───────────┤
│ 上传  │ 100    │ 100    │ —      │ —         │
│ 解析  │ 95 95% │ 98 98% │ +3pp   │ 12s/8s    │ ← 灰测快
│ 编辑  │ 80 80% │ 70 70% │ -10pp  │           │ ← 灰测编辑多?异常
│ 审核  │ 75     │ 65     │        │           │
│ 审批  │ 70 70% │ 60 60% │ -10pp  │           │
│ 入库  │ 68     │ 58     │        │           │
└──────┴────────┴────────┴────────┴───────────┘
卡点：编辑→审核 灰测组掉 10pp，建议调查
```

> 漏斗分组对比是灰测效果 diff 的另一面：**指标看"质量"，漏斗看"流程"**。灰测组准确率高但漏斗掉得多，说明新模型虽然准但慢/难用，不该推全。
