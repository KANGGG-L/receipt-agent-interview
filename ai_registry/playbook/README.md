# Playbook：怎么改 Agent 的经验库

> **定位**（Gap C1）：把「评测发现问题 → 提出假设 → 改动 → 验证 → 结论」
> 的完整决策链固化为可复用条目，让「飞轮转过一圈」从口头叙事变成可查档案。
> 本目录是 Playbook 的**模板与索引**；具体条目按主题分文件归档。

---

## 一、条目模板（六栏，缺一不可）

每条 Playbook 记录必须包含以下六栏。**数字必须给出处**（评测报告路径、
`prompt_eval_history.json`、测试文件名）；查不到出处的数字一律标「待补」，
禁止凭印象补数。

| 栏位 | 含义 | 填写要求 |
| :--- | :--- | :--- |
| **触发评测** | 哪次评测/哪个失败样本暴露了问题 | 给出评测集 / 报告路径 / 失败样本特征 |
| **假设** | 一句话可证伪的改动假设 | 「若……则……」句式，避免笼统「优化」 |
| **改动 diff** | 实际改了什么 | 版本号 + 文件路径 + 关键 prompt/代码片段摘要 |
| **val 结果** | 改动后在验证集上的数字 | 准确率 / CER / 拦截率等，带出处；无则「待补」 |
| **结论** | 有效 \| 无效 \| 回归 | 三选一；回归必须说明回退动作 |
| **下次别再试** | 沉淀反面经验 | 已证伪的路径，防止重复踩坑 |

## 三、口径红线（写任何条目都必须遵守）

1. **禁止「实现了自进化闭环」表述。** 准确说法：闭环骨架与门控已全部打通，
   评测信号能自动流进记忆与改进链路；但**改进方案的生成与最终确认仍在人手上**，
   这是当前阶段的主动设计，而非能力缺失。
2. **准确率数字必须带 GT 状态说明。** 当前对外 98.2% 是对着 **AI 草稿 GT**
   （`gt_status=draft`）刷出来的；人工确认后的数字待出，大概率更低但可信度更高。
   引用时必须注明 GT 口径。
3. **不写真实商户数据。** 供应商名、金额、单号一律脱敏或用合成样本替代。
4. **回归条目必须留回退证据。** 说明回退到哪个版本、为什么、是否保留 schema。
